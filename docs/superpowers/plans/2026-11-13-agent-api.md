# Agent API and MCP Server (Plan 4 of 6) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** An agent that already reads order confirmations can read what to buy and write back what was ordered, without ever seeing a protected gift, a Santa flag or a board. Scoped API tokens, a small REST API under `/api/v1` that authenticates by bearer token only, and an MCP server over that API that runs as its own service.

**Architecture:** Schema version 4 adds `api_tokens` and `gift_agent_log`. `tokens.py` makes, lists, revokes and checks tokens (only a SHA-256 hash is stored). `agent.py` is the route-free logic of `/api/v1`: what each scope may read and write, the scope's view of a gift, and the audit note. Its routes, and the three token-management routes the web app uses, sit in two separate blocks of `app.py`; the request guard gains one narrow branch for `/api/v1`. The MCP server (`mcp_server.py`, `mcp_http.py`, and `mcp_remote.py` copied verbatim from `mcp-server-shared` as Matinee does) calls the REST API with one token and never opens the database; the installer adds it as a second service with its own user, pip venv and config. The frontend gains `tokens.js` (an "Agent tokens" screen) and an agent-notes line on the gift's order card.

**Tech Stack:** as the core plan. The MCP service only: `mcp>=2.3,<3`, `uvicorn`, `pyjwt[crypto]` from `requirements-mcp.txt`, in its own venv (there is no Alpine package); the Flask app gains no dependency.

**Spec:** `docs/superpowers/specs/2026-11-12-gift-tracker-design.md`, "Agents". Builds on the core, school (`2026-11-13-school-instance.md`, schema 2) and after-purchase (`2026-11-13-after-purchase.md`, schema 3) plans. None of them is edited here.

## Decisions fixed before the build

- **Schema 4** (the issue reserved 5; the queue assigned 4, since 2 and 3 are the school and after-purchase schemas). `api_tokens(id, name UNIQUE, scope CHECK IN ('delivery','shop','full'), token_hash UNIQUE, unlocked INTEGER NOT NULL DEFAULT 0, created_at, last_used_at, revoked_at)`; `gift_agent_log(id, gift_id → gifts ON DELETE CASCADE, token_id → api_tokens, at, action)`. `unlocked` is the one column beyond the issue's list (see "full and the lock"). A name stays taken after revoke, so the audit trail never names two tokens alike.
- **A token** is `gt_` plus 32 random bytes, URL-safe base64 (`secrets.token_urlsafe(32)`); it is returned once, by the create call, and never again. Only `sha256(token).hexdigest()` is stored. A lookup hashes the presented token and selects by hash; `last_used_at` is written on each authenticated request.
- **Token management is web-only and needs the unlock.** `GET /api/tokens`, `POST /api/tokens`, `DELETE /api/tokens/<token_id>` (revoke: sets `revoked_at`, keeps the row) are ordinary `/api/` routes behind the Cloudflare identity guard and the CSRF checks, and all three are `@unlock_required`: a `full` token is as strong as the PIN, and the list names what agents exist. A token cannot reach them (it has no Cloudflare identity). School mode has no lock, so there `unlock_required` passes, as for every other route.
- **`/api/v1` authenticates by bearer token only.** The guard's branch for `/api/v1` and `/api/v1/...`: `Authorization: Bearer <token>` naming a known, unrevoked token admits the request as that token (`g.token`), and nothing else does. Cloudflare identity is never consulted and never admits; the `gt_unlock` cookie is never read (`g.unlocked` is set from the token before any view runs, so `app.unlocked()` cannot fall through to the cookie); `slide_unlock` sets no cookie (there is no `g.user`). Mutations need a JSON object body but not `X-Tracker` or `Origin`: a bearer header is never sent by a browser on its own, so there is no CSRF to guard against.
- **401 versus 403 on `/api/v1`.** A request that presents nothing at all (no `Authorization`, no Cloudflare header) gets the guard's usual `403 {"error": "Forbidden"}`, so `tests/test_identity.py`'s LAN walk (every rule, 403) holds unchanged. A request that presents a credential that is not a valid bearer token (a Cloudflare JWT, a malformed header, an unknown or revoked token) gets `401 {"error": "Unauthorized"}` with `WWW-Authenticate: Bearer`. Both say nothing about which tokens exist.
- **A token gets nothing outside `/api/v1`.** Every other path still requires the Cloudflare identity; a bearer token alone there is 403 like any anonymous request.
- **Scopes.** One table, `agent.SCOPES`:

  | Scope | Reads gifts in status | Lists by default | May set status | Other reads | Writes |
  | --- | --- | --- | --- | --- | --- |
  | `delivery` | decided, ordered, arrived | decided, ordered | arrived | occasions, addresses | order fields |
  | `shop` | idea, decided, ordered, arrived | idea, decided, ordered | ordered, arrived | + people, budgets | order fields |
  | `full` | every status, both tracks | every status | any | + people, budgets | order fields, new gifts |

  `delivery` also reads `arrived` (the issue says decided or ordered) so that it can see the gift it just marked arrived and correct a delivery date; arrived gifts are not in its default list. A gift outside the scope's statuses answers the same 404 as a missing gift. An operation outside the scope is `403 {"error": "This token's scope does not allow that.", "scope": "<scope>"}`.
- **What a gift looks like to each scope.** `delivery`: `id, occasion_id, title, status, store, recipients [{id, name}]`, the order keys of `orders.to_json` and `ship_to` (the address label). `shop` adds `url, price_cents, notes`. `full` is the web app's gift JSON plus `recipients` and `ship_to`; it has `santa` only when the token sees protected gifts, and location keys only in family mode. No scope below `full` ever gets `santa`, `location_id`, `location_path`, givers or `created_by`.
- **The lock.** Every token below `full` is locked, always: lists filter on `gifts.PROTECTED_SQL`, single-gift routes check `gifts.visible()` first and answer 404, people and budgets leave protected people out, and a write to a protected gift is 404 like a missing gift. There is no `/api/v1` route for boards, assignment or hiding places.
- **`full` and the lock.** The web app needs the PIN for protected data, so a `full` token sees protected gifts and `santa` only when it was created with `{"unlocked": true}`. Creating one needs the unlock like every token route; `unlocked: true` is 400 on any other scope and in school mode (there is no lock there). A `full` token without it is locked exactly like the others; for it a protected person is the same as a missing one (`400 "No such person."` when named as a recipient), and `santa` in a body is 403.
- **`full` is the v1 operations, unrestricted; not the whole web API.** The spec says `full` is "everything the web app can do". Here it means: every `/api/v1` operation, every status, plus creating a gift. Editing people, occasions, boards and hiding places stays in the web app. Mirroring the whole web API under bearer auth would double the surface the privacy walk has to cover; the owner's agent needs to capture ideas and record orders, which this covers. Stated as a deviation in the PR.
- **Order fields are written through `orders.update` and `gifts.set_status` only.** `PATCH /api/v1/gifts/<gift>/order` takes only `orders.FIELDS` (any other key is 400, with a message that lists the order fields and never echoes the caller's keys); `POST /api/v1/gifts/<gift>/status` passes the rest of its body to `gifts.set_status(con, id, status, order, actor=<token name>)`, so marking ordered needs seller, ship-to and eta exactly as in the web app and sets `ordered_by` to the token's name.
- **Every write by a token leaves an audit note**: a `gift_agent_log` row with the token and an action (`order: seller, eta`, `status: ordered`, `created`), written with the write: in the same transaction for an order patch, and straight after `gifts.set_status` (which runs its own transaction) for a status. The web app's gift JSON gains `agent_log: [{at, token, action}]` (newest first, both modes) and the order card shows it. `ordered_by` is set as well when the write marks the gift ordered.
- **Path arguments** in `/api/v1` are named `gift` and `occasion` (not `gift_id`, `occasion_id`). `tests/test_privacy.py` walks every `/api/` rule with a Cloudflare identity and no token; on `/api/v1` that is always 401, and its write walk expects 404 or 423 for a protected `gift_id`, an assertion about the browser's lock that does not apply to a surface the browser cannot use. The bearer walk in `tests/test_agent_privacy.py` asserts 404 for protected gifts there. `args()` gains `gift`, `occasion` and `token_id`.
- **School mode.** All three scopes exist; no v1 response carries `santa` or a location key (whatever the token or the column says), `unlocked: true` on a new token is 400, and a body naming `santa` is 400 as in the web app. No v1 route is mode-specific, so `FAMILY_ONLY` and `SCHOOL_ONLY` do not change; `tests/test_school.py` pins `tokens.scopes()` per mode and the v1 gift keys.
- **The MCP server** registers one tool per v1 operation that the token's scope allows (it asks `/api/v1/me` at start): `whoami, list_occasions, list_addresses, list_gifts, get_gift, update_order, set_status` for every scope, plus `list_people, get_budgets` for `shop` and `full`, plus `add_gift` for `full`. Tools call the REST API through `TrackerClient`; the client never opens the database. Errors become `ToolError` text without the token or an HTML body.
- **MCP over HTTP** follows Matinee: `mcp_http.py` serves Streamable HTTP behind its own Cloudflare Access application (`mcp_remote.py` checks the Access JWT, Host and serves `/healthz`), binds 127.0.0.1 (cloudflared runs in this container), path `/<service name>/mcp`, and refuses to start without `TRACKER_API_TOKEN` or with unsafe HTTP settings. `python mcp_server.py` is the stdio form for a local client.
- **Installer.** A second service per instance, `$NAME-mcp`: user `$NAME-mcp` (no data access), venv `/opt/$NAME-mcp/venv` from `requirements-mcp.txt` (a pip or network failure only skips the MCP service), config `/etc/conf.d/$NAME-mcp` (root, 0600: holds the token), init script from a template between `# mcp-initd-begin` and `# mcp-initd-end`, port 8779 (8780 for a named instance) unless the config says otherwise. It starts only once `TRACKER_API_TOKEN`, `CF_ACCESS_AUD` and `MCP_PUBLIC_HOSTS` are set. The Flask app's service script, settings list and `settings.py` do not change (the MCP settings live in the MCP service's own config, not in the app's).
- **Cloudflare.** Requests to `/api/v1` from outside still pass the tracker's Access application. `docs/mcp-setup.md` documents an Access policy on the path `/api/v1` with the Service Auth action and a service token (preferred), or Bypass (the bearer token is then the only gate). The MCP service reaches the app on loopback and needs neither.
- **Tests for the MCP package.** `mcp` is not installed in the app's venv. `mcp_server.py` imports it under `try`, so the client and every REST round-trip are tested in the main suite against the Flask test client; the FastMCP and HTTP tests `importorskip` (as Matinee's do). CI installs `requirements-mcp.txt` in the Python jobs and the Alpine job, and a separate step runs `tests/test_mcp_*.py` with JUnit output and fails if any test was skipped.

## Review Focus

1. A token below `full`, and a `full` token created without `unlocked`, never receives a protected gift (title, store, order fields), a `santa` key, a location key or a protected person, on any `/api/v1` route with any method; a write aimed at a protected gift is 404 like a missing gift and changes nothing. (Task 4: the bearer walk over `app.url_map`.)
2. `/api/v1` admits a bearer token and nothing else: a valid Cloudflare JWT without a token is 401, the `gt_unlock` cookie of an unlocked browser does not unlock a token, a revoked or unknown token is 401, and a token presented anywhere outside `/api/v1` is 403. (Task 3.)
3. Each scope is refused (403) an operation above it, and a status above it, and changes nothing when refused: `delivery` cannot mark ordered or create a gift, `shop` cannot create a gift or set `given`. (Task 4.)
4. Creating, listing and revoking tokens needs the unlock; the token is shown once and only its SHA-256 hash is stored; `unlocked: true` is refused for any scope but `full` and in school mode. (Task 3, Task 5.)
5. Every write by a token is recorded with the token's name (audit note, and `ordered_by` when it marks ordered), and order fields go only through `orders.update` / `gifts.set_status` with the same "ordered needs seller, ship-to and eta" rule as the web app. (Task 4.)
